# Init-cadence values are retained in volatile RAM, never in flash

The decision: the nine init-cadence entities — the identity strings `controller_firmware_version`, `product_code`, `appliance_serial`, `power_board_version`, `controller_model`, `hmi_firmware_version`, `hmi_model`, and the two setpoint bounds `setpoint_min` and `setpoint_max` — are captured as they are decoded, held in a retention block in uninitialised RAM, and republished at startup, so that an `esphome upload` does not blank them. They are deliberately **not** written to flash, neither through NVS nor through ESPHome's `restore_value`. A retained value is a cache of a past observation, never a reading: any live decode overwrites it, so a real initialisation burst always wins.

**The invariant this exists to protect is that a retained value must not survive a period during which the ESP was down while the appliance re-initialised.** Retention is harmless whenever we are listening, because any burst we observe overwrites what we retained — and the HMI runs its burst both when the appliance powers up and whenever MAIN disappears and comes back, so an ESP outage long enough for the HMI to notice produces its own burst. (The feature exists because an upload is *short* enough that the HMI does not notice.) The only way a stale value escapes is an ESP that was off while a burst happened that it therefore never saw. Volatile RAM covers that case and flash does not, which is why moving the block to NVS is not the harmless improvement it looks like. Any future change that makes these values survive power loss has to answer this paragraph first.

**The attribute is `__NOINIT_ATTR`, in DRAM — and only half of what it does here is an ESP-IDF guarantee.** Placement in `.noinit` was confirmed from the linker map rather than assumed. ESP-IDF documents such data as something that "should keep its value after software restart", which is exactly the upload case, and the probe observed it holding across both an upload (reset reason `sw`) and a panic. The power-cycle half is **not** an ESP-IDF contract and must not be cited as one: it is one observation, on one board (Arduino Nano ESP32 / ESP32-S3, ESP-IDF 5.5.5, 2026-10-08), power removed for ten seconds — reset reason `poweron`, block rejected by its own guard, value absent rather than stale or garbage. The mechanism is unestablished; SRAM decay, the bootloader using that region as scratch, and the reset clearing it would all look like this, and the probe cannot separate them. It does not need to, because all three give what the invariant asks. Ten seconds is also the *shortest* off-time tried, while the exposure that matters is an outage long enough for the appliance to have re-initialised — minutes.
